# Guide: i18n and l10n

`github.com/angvp/tango/i18n` is tanGO's small, opt-in translation layer. It translates text by symbolic key, keeps the English fallback inline in Go source, and stores the resolved locale on the request's standard `context.Context`.

It is intentionally not a full locale framework: no gettext pipeline, no extraction CLI, no plural rules, and no locale-aware date/time/number/currency formatting.

## Translating text

Use `i18n.T` anywhere you have a `context.Context`:

```go
message := i18n.T(ctx.Context(), "books.title", "Books")
```

The signature is:

```go
func T(ctx context.Context, key, fallback string, args ...any) string
```

`T` resolves in this order:

1. Use the request locale's catalog when it has `key`.
2. If the locale has a region, try the base language catalog (`es-MX` → `es`).
3. Return `fallback`.

The fallback is the permanent English source of truth. If no i18n middleware is installed, no catalog exists, or a catalog misses a key, the app still renders the inline fallback.

For dynamic text, use `fmt.Sprintf`-style placeholders:

```go
title := i18n.T(ctx.Context(), "admin.create.title", "New %s", meta.Name)
```

The same placeholders must exist in translated catalog values:

```go
i18n.RegisterCatalog("es", map[string]string{
    "admin.create.title": "Nuevo %s",
})
```

A translation may reorder arguments with explicit indexes, and flags, width and precision are free:

```go
// fallback "%s of %s"
"%[2]s de %[1]s"
```

`T` compares the verbs a catalog value uses with the fallback's, argument by argument. A value that is empty, or that omits, adds or changes a verb, is treated as missing: `T` tries the base language and then returns the fallback, so a mistranslated catalog degrades to English instead of printing `%!s(MISSING)`. A literal percent sign in a fallback must be written `%%` once it is formatted; a fallback that is itself malformed is the host's own mistake and its translations are trusted as before.

## Catalogs

Catalogs are plain Go maps registered explicitly:

```go
i18n.RegisterCatalog("es", map[string]string{
    "admin.login.title": "Administración tanGO",
    "admin.button.save": "Guardar",
})
```

Multiple calls for the same locale merge per key. If two catalogs register the same key for the same locale, the latest value wins. Different locales stay isolated.

A reusable app can register its own catalog from its `Register` function by convention:

```go
func New() tango.App {
    return tango.NewApp("shop", func(registry *tango.Registry) error {
        i18n.RegisterCatalog("es", map[string]string{
            "shop.cart.title": "Carrito",
        })
        return registry.Routes().Include("/shop/", URLs)
    })
}
```

## Locale middleware

Locale resolution is request-scoped and explicit. Add `i18n.Middleware` to `tango.Config.Middleware`:

```go
config := tango.Config{
    InstalledApps: []tango.App{
        admin.New(store),
        shop.New(),
    },
    Middleware: []tango.Middleware{
        i18n.Middleware(nil), // nil uses Accept-Language
    },
}
```

`nil` uses `i18n.DefaultLocaleResolver`, which parses `Accept-Language` and chooses the best registered catalog using tanGO's simplified exact-then-base matching. For example, `es-MX` uses the `es-MX` catalog when present, otherwise `es`, otherwise the inline fallback.

Locales are compared without regard to case or to `-` versus `_`: `ES-MX`, `es-mx` and `es_MX` all select a catalog registered as `es-MX`, and the locale the middleware stores is the catalog's own spelling (the one used the first time that locale was registered). Registering `es-MX` and `es_mx` merges them into one catalog.

### Choosing the locale from more than the header

Most apps let the user pick a language. Compose the sources you want, in the order you want them tried; `Accept-Language` is always the last fallback:

```go
config.Middleware = append(config.Middleware,
    i18n.MiddlewareResolver(i18n.Chain(
        i18n.FromQuery("lang"),  // ?lang=es is a one-request override
        i18n.FromCookie("lang"), // the saved choice
    )),
)
```

- `FromQuery(param)`, `FromCookie(name)` and `FromHost(map[host]locale)` each return a locale only when it has a registered catalog, so a value such as `?lang=xx` or a tampered cookie never reaches the request. They read the request; they never set a cookie or store a preference. Your own view sets the cookie.
- `FromHost` copies its map when you build it and compares hosts in lower case without port or trailing dot.
- `Chain` skips an answer that has no catalog and tries the next resolver, ending with `Accept-Language`.
- `FuncResolver(f, "Cookie")` wraps your own function (a session, a path prefix, an account preference) and names the headers it reads.

Each resolver reports the request headers its answer depends on through `Vary()`; `Chain` unions them with `Accept-Language`. Path prefixes are routing, so they stay in your routes and a `FuncResolver`.

You can also pass a plain function to `i18n.Middleware`:

```go
resolver := func(r *http.Request) string {
    if cookie, err := r.Cookie("locale"); err == nil {
        return cookie.Value
    }
    return i18n.DefaultLocaleResolver(r)
}

config.Middleware = append(config.Middleware, i18n.Middleware(resolver))
```

A plain function cannot say what it depends on, so nothing marks the response with `Vary` for it; prefer `FuncResolver`.

No first-party app wires this automatically. Admin calls `i18n.T` internally, but it renders English fallbacks until the host registers catalogs and middleware.

## Caching and response headers

The middleware tells caches and clients what it did:

- **`Vary`.** With `Middleware(nil)` every response carries `Vary: Accept-Language`, so a cache or CDN in front keeps one copy per language. `MiddlewareResolver(Chain(...))` sends the tokens its resolvers need: `Cookie` for `FromCookie`, `Accept-Language` for the built-in fallback, nothing for `FromHost` (the host is already part of what a cache keys on) and nothing for `FromQuery` (the query string is part of the URL). The tokens are merged with any `Vary` header already on the response, ignoring case, never repeated, and a `*` already there is left alone.
- **`Content-Language`.** Set only when a catalog was selected for the request, to that catalog's locale, and never over a value something else has already set. A request that resolves no language gets none.

A plain function passed to `i18n.Middleware` cannot say which headers it reads, so no `Vary` is added for it. If it reads a cookie or header, use `FuncResolver(f, "Cookie")` with `MiddlewareResolver` so caches see it. With no i18n middleware installed, responses are exactly what they were.

## Finding untranslated text

`i18n.OnMissing` tells you what a locale has not translated while you run the app in it:

```go
i18n.OnMissing(func(locale, key string) {
    log.Printf("untranslated: %s %s", locale, key)
})
```

It is called when the resolved locale has a catalog (or a base-language one) but none supplied usable text for the key: the key is absent, its value is empty, or its verbs do not match the fallback's. A locale with no catalog at all is not reported, since the host never translated it. Each (locale, key) pair is reported at most once for the life of the process, the hook is `nil` by default, and `OnMissing(nil)` clears it.

The callback runs on the goroutine that called `T`, outside this package's locks, so it may call `T` or `RegisterCatalog`. A panic in it is not recovered. Use it in development and tests rather than in production request paths.

## Checking catalogs against the code

`T` records each key with its fallback the first time it runs with a resolved locale (an app with no locale resolved pays nothing). Two functions read that record:

- `i18n.Keys()` lists the observed keys and fallbacks, sorted by key.
- `i18n.Validate()` checks every registered catalog against them and returns a `Report`.

`Report.Problems` are defects, sorted by locale and key: `ProblemMismatch` (a value's format verbs differ from the fallback's, so `T` ignores it), `ProblemEmpty`, `ProblemConflictingFallback` (one key observed with two fallbacks) and `ProblemRegistryFull`. `Report.Unobserved` lists catalog keys that no observed call uses, usually a typo; it is advice, not an error, because a page that did not run leaves its keys there.

Validation covers only what has run in this process. It is not a startup or static check, so exercise the pages in the locale first, as a test does:

```go
for _, path := range []string{"/admin/", "/admin/books/"} {
    get(t, path, "es") // request with the locale resolved
}
if report := i18n.Validate(); len(report.Problems) != 0 {
    t.Fatalf("%+v", report.Problems)
}
```

A test that has walked every page may also fail on a non-empty `Unobserved`.

The registry holds at most 4,096 distinct keys. Translation fallbacks must be stable literals, never request- or user-derived text; a program that exceeds the limit stops recording new keys and `Validate` reports `ProblemRegistryFull`.

## Testing

Catalogs, the `OnMissing` hook and the observed keys are process-wide state. In a test, call `i18ntest.Isolate(t)` (from `github.com/angvp/tango/i18n/i18ntest`) first: it starts the test with everything empty and restores the previous state in `t.Cleanup`.

```go
func TestSpanishAdmin(t *testing.T) {
    i18ntest.Isolate(t)
    i18n.RegisterCatalog("es", spanishCatalog)
    // ... exercise pages, then i18n.Validate()
}
```

Because the state is shared by the whole process, a test that uses `Isolate` must not call `t.Parallel()`, and should not run beside a parallel test that uses `i18n`.

## Key naming

Use explicit symbolic keys, not English text as keys.

Good keys are namespaced by owner and surface:

- `admin.login.title`
- `admin.button.save`
- `shop.cart.empty`

This keeps English copy editable without breaking existing catalogs.

## What the admin translates

When a request has a selected catalog, the admin pages declare it in `<html lang>` (the catalog's registered spelling; `en` otherwise), and the built-in Markdown and JSON widgets, their field errors and the Markdown preview endpoint's messages all go through `T`:

- `admin.widget.view_label` (`%s view`), `admin.json.*` (`tab_edit`, `tab_formatted`, `apply`, `status_nothing`, `status_invalid`, `view_invalid`, `status_applied`), `admin.error.json_invalid`, `admin.error.json_syntax`
- `admin.markdown.*` (`tab_write`, `tab_preview`, `preview_title`, `count`, `count_max`, `preview_failed`, `preview_unavailable`, `preview_rendering`, `document_title`) and `admin.preview.*` (`too_large`, `unreadable`, `not_utf8`, `timeout`, `failed`, `output_too_large`)

Messages the widget script shows in the browser use `{count}`, `{max}` and `{error}` placeholders instead of format verbs, so keep those names in the translation (`"{count} de {max} caracteres"`). `Validate` does not check braces. Unwired apps render exactly the markup they did before.

## Not supported

- Pluralization: tanGO has no plural-rule engine yet; use separate simple keys when needed.
- Date/time formatting: HTML form controls still use browser-required formats such as `datetime-local`.
- Number/currency formatting: use app-level formatting for now.
- File-based catalogs: catalogs are Go source maps only; JSON/YAML/gettext loading can be layered on later without changing `T`.
- Automatic locale storage: no cookie, session, or account preference resolver ships by default, but `LocaleResolver` makes those easy to add in app code.
