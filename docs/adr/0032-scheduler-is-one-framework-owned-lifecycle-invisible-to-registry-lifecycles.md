# The scheduler is one framework-owned Lifecycle, appended last and invisible through `Registry.Lifecycles()`

`ServeContext` drives every registered `Job` through a single internal `Lifecycle` it appends itself — after every host-registered `Lifecycle`, and only once `Registry.RegisterJob` has been called at least once — rather than a Lifecycle the host constructs and registers by hand, and rather than a value `Registry.Lifecycles()` ever returns. The obvious alternative was the same shape `realtime.Hub` uses: expose a `tango.NewScheduler(jobs)` the host wires into `RegisterLifecycle` itself, matching the precedent in [ADR 0030](0030-lifecycle-is-explicit-registry-registration-not-an-optional-app-interface.md). We rejected it because jobs are declared the same declarative way models and routes are — an app calls `RegisterJob` inside its own `Register` callback and is done; requiring a *second*, separate wiring step for the scheduler itself reopens exactly the manual-integration gap lifecycle registration closed for `Hub.Close`, just for a different component.

Appending last, after every host `Lifecycle`, is deliberate ordering: the scheduler starts only once every host dependency a `Job` might reasonably want (a `db.Store`, a `realtime.Hub`, anything else wired via `Lifecycle.Start`) has already started, and — by the same reverse-order shutdown rule every `Lifecycle` already follows — stops *before* any of them, so a `Job` still finishing its last run never outlives a dependency it was using.

`Registry.Lifecycles()` never includes this entry: `ServeContext` computes `append(registry.Lifecycles(), schedulerLifecycle)` itself, for the list it actually drives, without ever mutating `registry.lifecycles`. A host introspecting `Lifecycles()` (for a test, a diagnostic, anything) should see exactly what it registered — not a synthetic entry it never asked for and cannot meaningfully act on. The scheduler's `Lifecycle.Name` is a reserved internal constant a host can never collide with by accident: `RegisterLifecycle` rejects it eagerly, at registration time, with a distinct `ErrReservedLifecycleName` (not `ErrDuplicateLifecycle` — the name isn't already taken by another registration, it's off-limits by construction), the same fail-fast convention every other `RegisterLifecycle` validation already uses.
