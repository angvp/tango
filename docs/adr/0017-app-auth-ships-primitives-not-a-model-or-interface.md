# Application auth ships composable primitives, not a default User model, an interface, or a login view

`auth` gives ordinary tanGO apps a login/logout/current-user foundation, distinct from admin-only login. The shape of that foundation was the central decision, and it deliberately breaks from how frameworks like Django do this (a base `User` model apps extend, or an `AuthenticationBackend` interface apps implement).

**No default `User` model, no interface.** `AdminUser` is deliberately narrow — username and password only — because admin's own needs are narrow. An application's "user" almost always wants different or additional fields (email, display name, whatever the app's domain needs) from day one, so a fixed tanGO-provided model would be outgrown immediately; per [minimal ORM foundations](../guides/relationships-and-admin-foreign-keys.md) and the "plain Go structs as source of truth" principle, tanGO doesn't own that schema. An interface-based alternative (an app implements `Authenticator` or similar, tanGO calls into it) was also rejected: nothing else in tanGO works this way — `db.Store`'s methods are generic over explicit `model.ModelMeta` values, not behind an interface an app satisfies, and introducing the first "pluggable business logic" interface in the codebase for this one feature would be a bigger, less consistent commitment than the problem needs.

**No signup view, no login view.** Mirrors admin's own posture: `AdminUser` rows are created only via the `tango admin` CLI, never a self-service form, because account-creation UX (validation, duplicate handling, which fields to collect) varies too much for tanGO to own well. The same reasoning applies even more strongly to login itself once JSON APIs are considered: a JSON API's "login" returns a token/session cookie from a POST handler, an HTML app's is a rendered form — genuinely different shapes, not two skins on one view. `auth` ships the primitives (password hashing, session create/lookup/delete, CSRF, safe-redirect, a `RequireLogin` route wrapper) an app composes into whichever view shape it needs, the same way `admin/login.go` itself is just glue code over lower-level primitives.

**Session storage follows a fixed-field-name convention via reflection, not new struct tags.** An app's session model must be named `Token string`, `UserID <T>` (tagged `tango:"fk=YourUserModel"`), `ExpiresAt time.Time`, plus the usual `tango:"pk"` field — `auth.CreateSession`/`SessionUser`/`DeleteSession` find these by `reflect.Value.FieldByName`, directly mirroring `AdminSession`'s existing shape rather than inventing a new mechanism. Extending the `tango` struct tag vocabulary (e.g. `tango:"session-token"`) to let an app name these fields freely was considered and rejected: it would grow model-tag grammar for one feature's narrow need, when matching an existing, already-precedented shape costs nothing to document.

**Consequence: admin and application identities are always separate.** There is no mechanism to share `AdminUser`/`AdminSession` with an app's own model — `AdminSession.UserID` is permanently wired to `AdminUser` specifically, and an app's own session model is wired to its own user model the same way. An app wanting overlap between "admin" and "logged-in customer" builds that itself (e.g. its own explicit foreign key to `AdminUser`); tanGO provides no built-in bridge.

Considered and rejected, together: a Django-style base `User` model apps extend; an `Authenticator`/similar interface; a ready-made login/signup view; new session-role struct tags. All four would have made `auth` a bigger, more opinionated commitment than "give apps the pieces," which is what was actually needed.

**Later:** the `accounts` app ([ADR 0020](0020-accounts-is-a-conventional-identity-app-not-an-app-permissions-framework.md)) ships ready-made register, login and logout views as an optional, installable app built on these primitives. `auth` itself still ships primitives only.
