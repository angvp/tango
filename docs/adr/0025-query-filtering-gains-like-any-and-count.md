# Query filtering gains `OpLike`, one OR group, and `Store.Count`

This widens the `Where`-only primitive (see [ADR 0024](0024-query-filtering-is-a-bounded-where-primitive.md)) with `db.OpLike` (string fields only, a raw SQL `LIKE` pattern — no automatic wildcard escaping, no case-folding guarantee across dialects) and `db.Query.Any`, one OR group combined with `Where` via AND. `Store.Count(ctx, meta, query)` applies the same `Where`/`Any` filters, ignoring `Limit`/`Offset`/`OrderBy`, to return a pagination total.

The trigger was concrete, not speculative: admin's `Options.Search` and its paginator's row count both still ran on hand-written raw SQL after `Where` shipped, because the bounded `Where`-only primitive genuinely couldn't express `LIKE`-across-several-fields-ORed-together. Rather than leave two competing filtering mechanisms in the codebase indefinitely (`Where` for typed comparisons, permanent raw SQL for search), we widened the primitive just enough to retire the raw-SQL duplicate and migrated admin search/count and the accounts/session equality lookups onto it. `Any` stays a single flat OR group — no nesting, no arbitrary boolean trees — the same "smallest primitive that unblocks a real caller" discipline ADR 0024 used, applied a second time now that a real caller (`Options.Search`) forced the question. `IS NULL`, joins, cross-model filtering, and `Store.Get` filtering remain out of scope, unchanged from ADR 0024.
