# `accounts` is a conventional identity app, not an app-permissions framework

`accounts` is tanGO's first-party, optional, installable reusable app, giving projects a ready-made email/password register/login/logout flow, built on the `auth` primitives from [ADR 0017](0017-app-auth-ships-primitives-not-a-model-or-interface.md). Because it's the first framework-shipped thing that looks like "the app's user model," it's the natural place someone would expect roles, groups, or permissions to live — especially with `AdminUser.IsStaff`/`IsSuperuser` ([ADR 0019](0019-admin-only-boolean-tier-permissions.md)) sitting right next to it as a visible precedent for "a user-shaped model with a permission-shaped field."

**The decision: `Account` carries no permission-shaped field of any kind.** No `IsStaff`, no `Role`, no `Group`, no `Permission`, no generic `HasPermission` interface, no fixed-field-name convention `accounts` treats specially for authorization. `Account`'s entire shape is identity, credential, activity state, and a timestamp: `ID`, `Email`, `PasswordHash`, `Active`, `CreatedAt`. Nothing else.

**This extends ADR 0019, it does not reverse or reopen it.** ADR 0019 committed tanGO to owning no app-level permission primitive, specifically because the framework owned no app User model to hang one on — `AdminUser`'s two boolean tiers were scoped to admin precisely *because* admin is framework-owned and ordinary apps aren't. `accounts` now gives ordinary apps something that looks like a framework-owned User model for the first time. If `accounts` grew permission fields now, it would quietly re-litigate ADR 0019's conclusion through the back door: the same "no owned app User model to hang a primitive on" justification stops applying the moment `accounts` exists and has permission fields, without anyone having actually decided that a permission primitive is now in scope.

**An app that needs roles or permissions writes its own View wrapper against its own domain data — including, if it installs `accounts`, `Account` itself.** Nothing stops a project from adding its own `Role` model with a foreign key to `Account.ID` and writing a View wrapper that queries it; `accounts` just doesn't ship that model, that query, or that wrapper as part of the framework. This is exactly the same shape as ADR 0019's own resolution for admin: the primitive an app needs already exists (View wrapper, `auth.CurrentUserID`), the framework just doesn't own the permission *model*.

**The trade-off is intentional and accepted:** `accounts` is less batteries-included on authorization than a project migrating from Django or Rails might expect from a "user accounts" app. The alternative — even a minimal `IsStaff`-shaped flag "just in case" — would be exactly the kind of speculative field ADR 0019 already rejected once for `AdminUser`'s `IsSuperuser`, except here there's no forward-compatible justification (no admin-shaped bypass concept is known to be coming for `Account`); it would just be a permission primitive shipped before any real requirement forced its shape. Less framework-owned user-model complexity now is worth more than guessing at a permission shape most projects with real requirements will design differently anyway.

**Amendment (email verification):** `Account` gains `EmailVerifiedAt`, a nullable timestamp recording when the owner proved they receive mail at `Email`. It's identity state, not a permission: it gates nothing by itself, and an app opts in with `accounts.RequireVerified`. See [ADR 0045](0045-accounts-reset-and-verification-never-reveal-an-account.md).
