# `RequestID` middleware never trusts an inbound header unless a host explicitly opts in

`tango.RequestID` middleware always generates a fresh, `crypto/rand`-backed opaque ID by default, and always writes it to the fixed response header `X-Request-ID`. It does **not** read and trust an inbound `X-Request-ID` (or any other) header unless a host explicitly calls `WithTrustedHeader(name string)` naming that header — and even then, the inbound value is only used after validation (non-empty, bounded length, printable-ASCII safe set, no control characters/whitespace/commas/newlines); an absent or invalid trusted value silently falls back to generating a fresh ID rather than erroring or reflecting unvalidated content back to the client.

The alternative — trusting any inbound `X-Request-ID`-shaped header automatically, the common convention in many HTTP frameworks — was rejected because that header's value is attacker-controlled by default: a client can set it to anything, and if it flows unvalidated into every subsequent structured log line for that request, it becomes a log-injection and log-correlation-poisoning vector (an attacker forging IDs to collide with, or forcibly separate from, legitimate request traces). Requiring an explicit `WithTrustedHeader` call moves the trust decision to where it belongs — a host that knows its own upstream gateway/load balancer already generates and can be trusted to set that header — rather than making it the framework's default behavior for every request from every source.

`WithTrustedHeader`'s header *name* is validated once, at construction time, and panics on an invalid name (blank, whitespace, control characters, an invalid HTTP token) — a static host misconfiguration, not a runtime condition. Runtime inbound header *values*, by contrast, never panic regardless of content; an invalid one is simply ignored in favor of generating a fresh ID.
