# v0.1 covers every exported API except named exclusions

From v0.1.0, tanGO makes a written compatibility promise, published in `docs/compatibility.md`. The promise covers the Covered API. That is every exported identifier of every public package, plus three non-Go surfaces:

- every `tango` CLI command;
- every CLI app-side flag, including its JSON output and exit codes;
- the other surfaces the compatibility page lists: environment variables, the `tango:"…"` struct tag grammar, the `tango_migrations` schema, the View-error JSON body, the `accounts` HTTP endpoints, and observability metric and event names with their attribute keys and documented values.

Anything not named as an exclusion is covered. The exclusions are:

- `internal/`.
- The migration types and functions that exist for generated files and the CLI: the steps, the models, the schema state, and diff/replay.
- The best-effort admin extensibility already declared in ADR 0014, along with admin HTML, templates, CSS and URLs.
- The wording of error messages and logs. Sentinel errors stay covered.

Version numbers carry the promise:

- **Patch releases** never intentionally break the Covered API. The one exception is a security fix whose release notes say it does.
- **Minor releases** may break the Covered API, but only after a Deprecation window of at least one minor release. The deprecation is announced three ways: a Go `// Deprecated:` comment, a changelog entry, and the release notes.

Keyed struct literals are the supported way to build tanGO's structs; `go vet` already flags unkeyed ones. That lets a minor release add a field to a covered struct without a deprecation.

Two promises reach into the excluded migration surface:

- **The Generated-file contract.** A migration file written by any released `tango makemigrations` keeps compiling, being read by later runs, applying and rolling back on every later v0.x release. Tests on both dialects enforce this against migration files generated by every released version, kept in the repository.
- **Framework-owned models.** The `admin` and `accounts` models reach users' databases through their own `makemigrations`. A change to one ships only in a minor release, must be an added field or a Widening type change, and comes with upgrade instructions. A rename or drop of one of their fields goes through the Deprecation window.

Rejected:

- **An inclusion list** ("these packages are stable"). A package left off by mistake is silently unpromised, while a forgotten exclusion fails safe: it stays covered.
- **Counting every added struct field as breaking.** That would freeze `Config` and every options struct for no benefit to users who write keyed literals, which is what Go's own compatibility promise assumes.
- **Promising nothing until v1.0.** That is the situation this decision ends: a user can't tell what an upgrade will break.
- **Covering the migration step types outright.** They are shaped by the generator and change with it. Their stability is promised only for what the generator writes.

Consequences:

- Each release needs a dated `CHANGELOG.md` section.
- Releases come from a workflow that refuses a tag whose exact commit lacks a green CI run. On a patch tag, it also refuses any incompatible API change that `gorelease` reports.
- Every release adds its generator's output to the migration-file fixtures.
- The documentation site shows the latest release, not `main`.
