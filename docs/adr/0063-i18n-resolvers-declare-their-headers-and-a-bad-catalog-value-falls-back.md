# i18n resolvers declare the headers they read, and a bad catalog value falls back

## Context

[ADR 0022](0022-i18n-is-an-opt-in-override-layer-plain-go-maps-not-a-locale-framework.md) made `i18n` an override layer: English stays inline in Go source, catalogs are plain maps, and the host picks the locale with a function. That left four gaps once a real site used it. A cache in front of the app could serve one visitor's language to another, because nothing said the response depended on `Accept-Language` or a cookie. A catalog value with the wrong format verbs printed `%!s(MISSING)` or `%!(EXTRA …)` into a page. A missing key, or a typo in one, was invisible until someone read the page. And only `Accept-Language` could be matched against the catalogs, with no tolerance for `es_MX` or `ES-MX`. ADR 0022's estimate of the translatable surface ("a couple dozen short strings") no longer holds either: the admin and `accounts` pages, their errors and the account emails are well over a hundred keys.

## Decision

**A resolver names the headers its answer depends on.** `i18n.Resolver` has `Resolve(*http.Request) string` and `Vary() []string`. `FromQuery`, `FromCookie` and `FromHost` read one place each and return only a locale with a registered catalog; none of them writes a cookie or any state. `Chain` tries resolvers in the host's order and then `Accept-Language`, and its `Vary` is the union of theirs. `MiddlewareResolver` installs a resolver. The middleware adds the tokens to `Vary` (merged with what is already there, ignoring case, never repeated, `*` left alone, and merged again as the header is sent so a handler's own `Vary` cannot duplicate it), and sets `Content-Language` to the selected catalog's locale only when a catalog was selected. A plain function still works and, because it cannot say what it reads, adds no `Vary`; `FuncResolver` lets it declare that. Choosing and remembering a language (a switcher, a cookie, an account setting) stays the host's job.

**Locale tags match without regard to case or `-` versus `_`,** and the locale the middleware stores is the catalog's own registered spelling, so `lang` attributes and `Content-Language` are stable.

**A catalog value that cannot stand in for its fallback is ignored.** An empty value, or one whose format verbs differ from the fallback's (argument by argument, positional `%[n]s` included), counts as missing: `T` tries the base language and then returns the English fallback. A translation can reorder arguments but cannot print garbage, and an email body that loses its `%s` link falls back rather than dropping the link.

**Missing and wrong text is observable, not silent.** `OnMissing` reports a missing translation once per (locale, key), outside the package's locks, and is off by default. `T` records each (key, fallback) pair the first time it runs with a resolved locale, bounded at 4,096 keys and allocation-free on the hot path; `Validate` checks every catalog against those pairs and reports mismatches, empty values, a key seen with two fallbacks and a full registry as problems, and catalog keys nothing used as advice. It covers only what has run in this process, which is why the documented use is a test that walks the pages. `i18n/i18ntest.Isolate` gives such a test an empty state and restores the previous one.

**tanGO ships no catalogs.** The admin and `accounts` render English until a host registers a catalog, and the worked Spanish examples live under `examples/`. Where the admin renders a locale, the page declares it in `<html lang>`; `accounts` does so only when a catalog was selected, so a project that never wires i18n renders the bytes it always did. The `accounts` HTML pages, their form errors and their emails go through `T` under `accounts.*` keys; an email is rendered in the language of the request that queued it (the locale is read when it is queued, before any account lookup, and the queued job keeps nothing else), and the JSON API's `error` text stays English because clients branch on `code`. Strings in the root package stay English: they are developer-facing errors and log text, not user interface.

**Catalogs stay Go maps, and plurals and formatting stay with the host.** File catalogs, plural rules and locale-aware number and date formatting are still not part of `i18n`; a host with a translator who does not write Go, or with counts that need plural forms, loads files or formats in its own code and registers the result, using separate keys per form.

**The compatibility promise covers keys and placeholders.** A key's name and its format placeholders (and the `{count}`-style placeholders the admin widget script uses) are part of the Covered API; the English fallback wording is not and may be corrected in any release.

## Consequences

A cache or CDN in front of a site that wires the middleware keeps one copy per language. A broken translation degrades to English instead of corrupting a page, and a host can fail its own tests on a missing or malformed key. The cost is that `Validate` is only as complete as the pages a test visits, that braces in script messages are not verb-checked, and that the observed-key registry is capped, so fallbacks must be stable literals rather than built per request. Choosing the language remains application code, which is more to write than a bundled policy and keeps `i18n` free of cookies, sessions and accounts.
