# Public `accounts` uses stricter/different security defaults than admin where the trust boundary differs

`accounts` reuses admin's existing security machinery wherever the underlying mechanism is identical (CSRF, safe-redirect) — an earlier review pass already promoted CSRF and safe-redirect into shared `internal/security` for this reason. But several places where admin made a specific security or correctness call, `accounts` deliberately makes a *different* one, because the two apps sit behind different trust boundaries: admin is reached by a small number of trusted operators running a CLI or logging into a backend panel; `accounts` is reached by the general public, self-registering over the open internet. Copying admin's defaults verbatim in every case would silently assume those trust boundaries are the same. They aren't, and treating them as if they were would either under-protect the more exposed surface or over-restrict the less exposed one.

**Login stays generic; registration doesn't.** Admin's login is deliberately generic — it never reveals whether a username exists, to close a credential-identification oracle. `accounts` keeps that same generic behavior for login. But `accounts`'s registration form says "this email is already registered" plainly on a duplicate signup, rather than staying equally non-committal. The two endpoints have different jobs: login is a credential *check* (an oracle there helps an attacker enumerate accounts to then attack); registration is a *self-service form* where a genuine user needs to know why their own signup didn't go through. An email address isn't a secret the way a password is, and an ambiguous "check your email" message for a flow that never sent an email is confusing UX bought for a small, accepted enumeration cost.

**`Active` is checked on every request through a valid session, not only at login.** `AdminUser` already behaves this way; `auth.SessionUser` itself does not, since it only resolves a session token to a raw user ID and has no notion of an `Active` field at all — any such check has to be implemented by whoever owns the user model, and `accounts` chooses to add it, matching `AdminUser`'s strict behavior rather than the looser "deactivation blocks new logins, but issued sessions ride out their natural expiry" alternative. This matters more for `accounts` than it might first appear: `accounts` sessions can last far longer than admin's (see below), so the gap between "deactivated" and "actually can't act anymore" is proportionally much larger if left unchecked.

**Duplicate-registration correctness relies on the database's unique constraint, not a `SELECT`-then-`INSERT` pre-check.** Admin's own `CreateAccount` does exactly that pre-check, and accepts the resulting TOCTOU race, because it's a trusted, operator-run CLI where two concurrent invocations creating the same username is a near-impossible scenario to actually hit. `accounts`'s registration form is exposed to the public internet, where two concurrent submissions for the same email are a realistic, if uncommon, event. Treating the database constraint as the actual correctness boundary (attempt the insert, translate a constraint violation into the user-facing "already registered" message) closes the race instead of merely narrowing it; a pre-check may still exist purely for UX, but nothing about correctness is allowed to depend on it.

**Admin's rate limiter is promoted into shared `internal/security` and reused by both apps.** The limiter itself (a small, per-IP, sliding-window failed-attempt counter) needed no behavior change — only its location, since it was previously private to the `admin` package and `accounts` needed the same protection on its own login and registration endpoints. Login and registration are both internet-facing surfaces that plainly need it; leaving `accounts` without the same protection admin already has, precisely because `accounts` is the more exposed of the two, would have been backwards.

**Session duration is allowed to differ from admin's, in the opposite direction from the points above — this one loosens, rather than tightens, relative to admin.** Admin's fixed 24-hour, no-remember-me session is a deliberate choice for an operator tool. `accounts` exposes a configurable duration with a 30-day default, because public users of an ordinary web app commonly expect to stay signed in across visits in a way an admin operator does not. This isn't a security-boundary difference the way the others are — it's a usage-pattern difference — but it's included here because it's the same underlying principle: don't copy admin's specific number when the reason behind that number doesn't transfer to `accounts`'s actual users.

Considered and rejected: copying every one of admin's specific choices verbatim, for consistency's own sake — rejected because "consistent with admin" isn't actually a goal anywhere in tanGO's design; matching the actual trust boundary is. Also considered: giving `accounts` its own separate rate-limiter implementation rather than sharing admin's — rejected for the same reason CSRF and safe-redirect were already shared, since it would recreate the exact "two implementations of one security mechanism in one module" problem that sharing already solved once.
