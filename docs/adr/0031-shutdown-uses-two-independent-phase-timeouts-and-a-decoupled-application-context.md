# Graceful shutdown uses two independent per-phase timeouts and a context decoupled from the caller's cancellation

`ServeContext`'s shutdown budget (`WithShutdownTimeout`, default 15s) is applied twice, independently — once as a fresh context bounding `http.Server.Shutdown`'s drain, and again as a second fresh context bounding the entire reverse-order lifecycle `Stop` pass — rather than as one shared budget split across both phases. A single shared context looked simpler at first: derive one `context.WithTimeout(parent, 15*time.Second)` and pass pieces of its remaining budget to each phase. We rejected it because HTTP draining and component shutdown have no principled way to share a clock fairly — if draining a slow client connection consumes the entire 15 seconds, components like `realtime.Hub` would receive an already-expired context and get no real opportunity to close peers or flush state, silently turning "graceful shutdown" into "abrupt shutdown that happened to call `Stop`." Two independent budgets mean a graceful shutdown can take up to roughly twice the configured timeout in the worst case — documented plainly, since a host tuning a container's overall termination grace period needs to account for it — but every phase always gets its full, real chance to finish cleanly.

Within the stop phase itself, every started `Lifecycle.Stop` call shares that one fresh context, in reverse registration order — not a fresh context per `Stop` call. A separate context per component was the first implementation and is wrong: with `N` components, worst-case shutdown time then grows to roughly `drain timeout + N × stop timeout`, unbounded by the number of registered components and contradicting the "roughly 2x, period" contract above. One shared context for the whole pass keeps the worst case at 2x regardless of `N`; a `Stop` that runs long simply leaves less time for the ones stopped after it, and once the shared deadline is hit, the remaining `Stop` calls still run — against an already-expired context — so they get a chance at immediate/best-effort cleanup rather than being skipped outright.

If the HTTP drain itself hits its deadline, `ServeContext` force-closes the server via `Server.Close()` — but still returns the drain-timeout error (wrapped, so `errors.Is(err, context.DeadlineExceeded)` still finds it), even though the forced close succeeded. Silently swallowing the timeout once the forced close worked was the first implementation, and it's wrong: a forced close means in-flight requests were aborted mid-response, which is not what "graceful shutdown succeeded" should mean to a caller checking the returned error.

The **application context** passed to every `Lifecycle.Start` (and retained by components for their own background goroutines) is built independently of the caller's `ctx`, using `context.WithoutCancel(ctx)` plus `ServeContext`'s own cancellation, rather than being a direct child of `ctx`. If it were a direct child, the instant the caller cancels `ctx` (the normal shutdown trigger) *after* startup has completed, every component's application-scoped goroutines would see cancellation *before* HTTP draining even begins — a request still in flight could find `realtime.Hub` or a DB pool already tearing down underneath it. `ServeContext` cancels the application context itself, deliberately, only after HTTP draining (and any forced close) has finished — drain first, then tear down components. Caller-set context values still flow through via `context.WithoutCancel`; only cancellation is decoupled, and only until `ServeContext` decides it's safe.

During startup, this decoupling is deliberately narrower: while a `Lifecycle.Start` is actually running, `ServeContext` *does* cancel the application context promptly the moment the caller cancels `ctx`, so a `Start` that cooperatively blocks on its received context (`<-ctx.Done()` from inside `Start`, where `ctx` is the Application context) can actually observe cancellation and return, instead of the Application context's deliberate detachment turning into an indefinite hang. `ServeContext` always waits for that `Start` call to finish before doing anything else — it never leaves it running unobserved, which would both leak the goroutine and risk a concurrent `Stop` call racing a still-running `Start`. Whether the interrupted component counts as "started" (and therefore gets `Stop` called during rollback) follows its own return value, not the fact that it raced with cancellation: a `Start` that returns a non-nil error (idiomatically its own `ctx.Err()`) is treated as failed/interrupted and excluded; one that still returns `nil` is treated as having genuinely finished and is included normally. This narrower coupling exists only for the duration of one `Start` call — once every component has started, the wider decoupling described above takes over for the rest of the run.
