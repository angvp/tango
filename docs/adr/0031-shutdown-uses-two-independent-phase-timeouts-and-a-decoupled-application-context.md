# Graceful shutdown uses two independent per-phase timeouts and a context decoupled from the caller's cancellation

`ServeContext`'s shutdown budget (`WithShutdownTimeout`, default 15s) is applied twice, independently — once as a fresh context bounding `http.Server.Shutdown`'s drain, and again as a second fresh context bounding lifecycle `Stop` calls — rather than as one shared budget split across both phases. A single shared context looked simpler at first: derive one `context.WithTimeout(parent, 15*time.Second)` and pass pieces of its remaining budget to each phase. We rejected it because HTTP draining and component shutdown have no principled way to share a clock fairly — if draining a slow client connection consumes the entire 15 seconds, components like `realtime.Hub` would receive an already-expired context and get no real opportunity to close peers or flush state, silently turning "graceful shutdown" into "abrupt shutdown that happened to call `Stop`." Two independent budgets mean a graceful shutdown can take up to roughly twice the configured timeout in the worst case — documented plainly, since a host tuning a container's overall termination grace period needs to account for it — but every phase always gets its full, real chance to finish cleanly.

The **application context** passed to every `Lifecycle.Start` (and retained by components for their own background goroutines) is built independently of the caller's `ctx`, using `context.WithoutCancel(ctx)` plus `ServeContext`'s own cancellation, rather than being a direct child of `ctx`. If it were a direct child, the instant the caller cancels `ctx` (the normal shutdown trigger), every component's application-scoped goroutines would see cancellation *before* HTTP draining even begins — a request still in flight could find `realtime.Hub` or a DB pool already tearing down underneath it. `ServeContext` cancels the application context itself, deliberately, only after HTTP draining (and any forced close) has finished — drain first, then tear down components. Caller-set context values still flow through via `context.WithoutCancel`; only cancellation is decoupled, and only until `ServeContext` decides it's safe.
