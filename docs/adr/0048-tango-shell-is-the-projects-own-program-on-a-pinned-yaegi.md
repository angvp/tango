# `tango shell` is the project's own program, on a pinned Yaegi

[ADR 0005](0005-yaegi-for-tango-shell.md) chose Yaegi as the direction for `tango shell`, and its 2026-10-09 update recorded what a spike found: the interpreter works against a scaffolded project, runs an older Go than the project, and has to run inside the project's own binary because only there are the project's model types linked. This ADR records how the shell was built on that.

**Decision.**

- **The shell is a program in the project's module.** `tango newproject` writes `shell/main.go`, about 25 lines plus a credential-free `databaseLabel`, which opens the database like `main.go` does and calls `shell.Run(ctx, config, store, os.Args[1:], shell.Options{…})` from the new public package `github.com/angvp/tango/shell`. `tango shell` builds that program and runs the binary with the arguments. It does not use `go run`, which reports every non-zero exit as status 1 and would lose the shell's own codes (2 for a bad command line, 130 for Ctrl-C). Only this program links Yaegi: the `tango` command, the server and every package of the root module other than `shell` do not, and a test fails if one starts to.
- **One package in the root module.** The public surface is `Run` and `Options{ReadOnly, Helpers, DatabaseLabel}`; the evaluator, formatter, helpers, history and terminal handling are in `internal/shellcore`. A nested module was rejected: it would need its own tags and release checks for a feature still finding its shape, and the cost it saves is a few extra lines in `go.sum`.
- **Application composition moves into the scaffold's `project` package.** `project.Config(store *db.Store) tango.Config` owns the installed apps, middleware and ordinary configuration; `main.go` and `shell/main.go` each load `.env`, open the database, build the store and call it. The server and the shell therefore register the same apps and models from one list. `Config` neither loads `.env` nor opens a database, so each process keeps its own database lifecycle and the shell can show which database it is on. A project made before this adds the files by one documented, tested, mechanical diff. Build tags and a copy of the app list in the shell were rejected: one hides the failure mode, the other drifts.
- **Map-based helpers, not generated symbol tables.** The session sees `Models`, `Describe`, `Get`, `List`, `Count`, `Create`, `Update`, `Delete` and `Context`, with models addressed as `app.Model` and rows as `map[string]any`. Generated typed access was rejected for v1 because the generated package silently describes the old struct after a model changes. A project's own functions come in through `Options.Helpers` as `project.Name`, with only plain values supported across the boundary.
- **Yaegi is pinned at the released v0.16.1.** Not a pseudo-version of its untagged master (the spike found both behave the same on what matters), and not a fork. A Yaegi upgrade needs a changelog entry, a rerun of the table of known limits (a test that fails when one of them starts to work) and the scaffold tests, and a docs change if what runs has changed.
- **Compatibility.** The command, its options and exit codes, `shell.Run` and `shell.Options`, the helpers and their documented shapes, `help()`, `exit()`, `quit()` and `TANGO_SHELL_HISTORY=off` are Covered. The interpreter and the Go subset it runs, formatting beyond sorted keys and one row per line, error and hint wording, the history file and the generated `project/` and `shell/` files are best-effort. See [versioning and compatibility](../compatibility.md).
- **It is not a sandbox.** The shell runs local developer code with the project's credentials. It starts no HTTP server, jobs or lifecycles. `--readonly` stops the built-in helpers that write; it is not a security boundary.

**Why.** The shell is worth having because it knows a tanGO application's registry and database, not because it runs arbitrary modern Go. That puts the entry point in the project, the surface in plain maps that need nothing generated, and the Go limits in a visible table that a test keeps honest.

**Consequences.** The root module's `go.mod` requires Yaegi, so every consumer's module graph lists it even if it never imports `shell`; only a binary that imports `shell` links it. The scaffold has two more directories, and existing projects need the one-time refactor to get a shell (and `tango newapp` keeps saying `main.go` for them). A tutorial and the `board` example list their apps in `project/project.go`. Ctrl-C during an evaluation ends the process, because the interpreter cannot interrupt a running evaluation. Moving off Yaegi later would still mean redesigning the evaluation loop, as ADR 0005 said, but the helpers, history and terminal handling around it would carry over.
