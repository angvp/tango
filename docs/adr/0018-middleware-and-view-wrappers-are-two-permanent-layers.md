# Middleware and View wrappers are two permanent, coexisting layers, not one unified mechanism

`tango.Middleware` is tanGO's first real middleware mechanism: `type Middleware func(http.Handler) http.Handler`, operating at the raw `net/http` layer, before `*tango.Context` exists. This is a genuinely new architectural layer: earlier docs explicitly stated tanGO "has no general middleware/chain mechanism," and route protection has, until now, been done entirely through [View wrapper](../reference.md)s — `func(tango.View) tango.View` functions like `auth.RequireLogin` and admin's `requireSession`, which operate on `*tango.Context` after it's built.

The central decision: **Middleware and View wrapper are two permanent, coexisting mechanisms, not stages of one migration.** Middleware owns raw HTTP cross-cutting concerns that don't need `tango.Context` at all — recovery, request IDs, logging, CORS, compression. View wrapper stays the idiom for anything that wants `*tango.Context` — auth, permissions, current-user lookup, redirects. Existing View wrappers (`auth.RequireLogin`, `requireSession`) are not migrated, deprecated, or reimplemented as `Middleware`; both mechanisms are documented as first-class, indefinitely.

**Why not unify into one mechanism.** Forcing `*tango.Context`-aware logic (auth's redirect-with-safe-`next`, current-user lookup) down to the raw `http.Handler` layer would mean reimplementing it against `http.ResponseWriter`/`*http.Request` directly, throwing away `Context`'s existing conveniences for no real gain — `Context` doesn't exist yet at that layer, by construction (`RouteRegistry.compile()` builds it per-request, inside the per-route closure chi dispatches to, after route params are resolved). Conversely, forcing raw HTTP concerns (recovery, request IDs) up through View wrapper would require every one of them to accept and thread a `tango.View`, when they have no need for anything `Context`-shaped and every existing net/http middleware package already targets the raw `http.Handler` signature. Two mechanisms at two natural layers cost less than one mechanism awkwardly spanning both.

**Consequence: `Middleware` is a plain, named `func(http.Handler) http.Handler` type — no tanGO-specific shape, no alias.** Any existing net/http middleware (chi's own `middleware` package, or third-party ones) works with zero adapter code, which is the entire point of naming that signature. A named type (not an alias) was chosen over a type alias purely for documentation clarity — `tango.Middleware` reads as an intentional tanGO concept in reference docs, matching how `tango.View` is already a named type — while remaining freely assignable from any unnamed `func(http.Handler) http.Handler` value, which covers the overwhelming majority of real-world middleware.

**Consequence: three attachment tiers, composed outer to inner as `global → group → route → view`.** `Config.Middleware` (global, wraps every compiled route including admin's — admin is not privileged; it contributes routes through the same public `Include`/`IncludeOption` mechanism any reusable app uses), `tango.WithMiddleware` on `Include` (per route-group), and `tango.Use` on `Path` (per route) map onto three configuration surfaces tanGO already has (whole app, mounted route group, individual route) rather than inventing a fourth. `admin.WithMiddleware`, mirroring `admin.WithBranding`'s existing functional-option shape, exists because admin owns its own internal `/admin/` `Include` call — a host has no other way to reach it, and without this option the only lever would be `Config.Middleware`, too broad for admin-only concerns like stricter rate limits or admin-specific security headers.

Considered and rejected: migrating View wrappers onto `Middleware` (throws away `Context`-awareness for no gain); a single per-app attachment point instead of three tiers (would force a real, likely-common need — admin-only or group-only middleware — into either "apply globally" or "fork admin.New," neither acceptable); a `tango.Chain` composition helper (pure convenience the ecosystem already provides, once `Middleware`'s stdlib shape makes those helpers directly usable); a pluggable on-panic hook on `tango.Recoverer()` (scope growth `Recoverer` doesn't need — it's ordinary `Middleware`, so an app wanting custom panic reporting just writes its own).
