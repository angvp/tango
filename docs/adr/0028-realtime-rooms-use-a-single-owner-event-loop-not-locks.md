# Realtime rooms use a single-owner event loop, not locks

`realtime.Hub` gives each active room exactly one goroutine that owns its membership, timers, and every call into host-supplied `Logic`. `Join`, `Leave`, `Dispatch`, `DispatchPeer`, timer expiry, and a peer writer's failed-`Send` report all become events funneled through that room's bounded inbound queue and processed one at a time. No other goroutine — a socket's read loop, its writer goroutine, a timer callback, a bot's scheduler — ever mutates room state directly; a writer that hits a `Send` error reports it as an event rather than touching membership itself. This removes an entire class of lock-ordering and partial-update bugs by construction, the same reason bubbletea (already a tanGO dependency) drives its own TUI state through a single-threaded update loop rather than a lock-guarded model.

The consequences are deliberate and worth knowing: `Join`/`Leave`/`Dispatch` block the caller until the room loop has actually applied the operation, not until network I/O completes. Delivery to a peer goes through its own bounded outbound queue, drained separately, so a slow peer gets closed rather than stalling the room. `ResetTimer` expiries carry a generation number, so a timer callback that was blocked waiting for queue capacity can never fire after `Logic` already reset that same timer. And there is no transactional rollback — deliveries a `Handle` call already made before returning an error stay made; `Logic` implementations must validate before emitting.

We rejected a conventionally locked `Room` struct — one where `Join`/`Leave`/`Dispatch`/timer callbacks each take a mutex and mutate state directly — because it pushes correctness onto every call site remembering to lock correctly and in the right order, instead of making incorrect concurrent access structurally impossible.
