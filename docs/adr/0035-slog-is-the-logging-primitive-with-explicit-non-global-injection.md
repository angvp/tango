# `*slog.Logger` is tanGO's logging primitive, injected explicitly per component, never as global mutable state

tanGO adopts `log/slog` directly as its logging contract — no framework-specific logger interface wraps it. A host configures the logger `ServeContext` itself uses (compiled-route error/panic-adjacent reporting, `Context.Logger()`, scheduler/Job-loop reporting) via `WithLogger(*slog.Logger) ServeOption`. Host-constructed `Middleware` (`Recoverer`, `AccessLogger`, `RequestID`) cannot receive that same value automatically — `Config.Middleware` is built inside a host's `Register` callback, before `ServeContext` ever parses its `ServeOption`s, so there is no point at which a later-configured logger could reach an already-closed-over middleware value. Each of those three middleware constructors therefore takes its own `*slog.Logger` explicitly via a `With*Logger` option, defaulting to `slog.Default()` when omitted; a host wanting one consistent logger everywhere passes the same value to all of them.

We rejected a package-level mutable logger var (the shape the first version of `reportJobFailure` used) once it became clear multiple `ServeContext` instances in the same process — routine in tests — would otherwise share and race over one process-wide logger. We also rejected inventing a `tango.Logger` interface: `*slog.Logger` is already the standard-library structured-logging contract, and wrapping it would only add an indirection layer with no framework-specific behavior to justify it.

Consequence: "the logger reaches everywhere" is not automatic. A host that configures `WithLogger` but forgets to also pass a logger to `Recoverer`/`AccessLogger`/`RequestID` gets two different loggers active at once (each defaulting to `slog.Default()` independently) — this is a deliberate, documented trade-off, not an oversight, in exchange for having no global mutable state to reason about.
