# Bounded strings are declared by tag, validated by rune count in Go, and enforced neither by SQLite nor by a `CHECK`

Every Go `string` used to map to `text`, so a title, a slug and a Markdown article looked identical to migrations and validation. A field with a real maximum now says so with `tango:"varchar=n"` (1 to 10,485,760, PostgreSQL's own ceiling). `tango:"text"` is accepted as explicit documentation, and a bare `string` stays unbounded text on every v0.x release: it generates no migration and keeps its SQL. A malformed tag fails `Register` with `model.ErrInvalidFieldTag`.

The limit is counted in runes (`utf8.RuneCountInString`; each invalid byte counts as one), which is how PostgreSQL counts `VARCHAR(n)`. `Store.Create` and `Store.Update` enforce it before any SQL runs and return a typed error that matches `db.ErrValueTooLong`, so the admin, the shell and `accounts` inherit it. The column is `VARCHAR(n)` on both dialects with no `CHECK`: PostgreSQL enforces the length itself, SQLite keeps the declared type without enforcing it, and raw SQL is documented as outside the guarantee. A bounded column is `Type: "varchar"` plus an additive `Length` (and `FromLength`/`ToLength` on `AlterColumnType`), so no packed type token is needed and generated files written before it still compile and mean what they meant.

Narrowing (`text` to `varchar(n)`, or a smaller `n`) is generated as an ordinary `AlterColumnType`. `ApplyPending` checks every narrowing in a migration before the migration's first step runs (undoing earlier renames in the same migration to find the physical names), so a refusal leaves the schema as well as the data unchanged; a direct `ApplyStep` keeps the same check. The check first streams each row's primary key and value through Go, counting with the Store's own rule, and fails before any DDL with the number of violating rows and one offending key. It never truncates or rewrites a value. Reversibility is decided per migration: a migration of narrowings is reversible, with widening `Down` steps; any widening makes the whole migration irreversible with no partial `Down`, because data written after a widening can make the reverse narrowing fail its own preflight.

Rejected:

- **A `CHECK (char_length(col) <= n)` constraint.** SQLite counts differently from PostgreSQL, a `CHECK` makes a later narrowing a table rebuild with a constraint to carry, and the Go check already gives the one cross-dialect answer.
- **Counting bytes, or asking the database for `length()`.** Bytes punish accents and emoji; `length()` and `CHAR_LENGTH()` disagree across dialects and encodings.
- **Defaulting bare `string` to `varchar(255)`.** It would change every existing application's schema.
- **A new Go type (`Text`, `Markdown`, `JSON`).** Those need admin and presentation semantics (M50) before they earn a model-level type.
- **Truncating on narrowing, or a reversible widening.** Both lose or reject data silently.

Consequences: a table needs a single primary-key column to be narrowed, because the error names an offending row by its key; on SQLite the limit exists only in Go, so a row written by hand-written SQL can exceed it; the preflight reads the table before the migration and is not atomic with concurrent writers (PostgreSQL's own `ALTER` still rejects a value that slipped in). The admin renders `maxlength`, which browsers count in UTF-16 units, so the server is the authority and the admin shows the server's per-field message. Built-in models are not retagged, since that would change every existing user's schema.
