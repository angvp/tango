# `ratelimit` ships a concrete token bucket, no storage interface yet

`ratelimit.Limiter` is a concrete, in-memory, per-process token bucket — there is no `Storage`/`Backend` interface behind it in v0.0.1, even though a Redis or other shared-state backend is an obvious, likely future need for hosts running more than one process. We considered defining that seam now, so a future backend could be dropped in without changing `Limiter`'s public shape, but rejected it: a correct distributed token bucket needs one atomic operation shaped like `Take(ctx, key, now, cost) (Decision, error)` — check-and-consume in one round trip — not a generic `Get`/`Set`/`Increment` store that `Limiter` composes calls against. Designing the interface before a real second implementation exists risks freezing the wrong shape: a naive `Get`/`Set`-style interface looks reasonable in isolation but can't actually express atomic consumption without a compare-and-swap dance that a purpose-built `Take`-shaped seam avoids entirely.

This follows the same discipline tanGO already applies elsewhere: avoid a speculative interface until a second concrete implementation exists to prove its shape. When a real distributed backend is built, the seam it introduces should look like the `Take` signature above — a single atomic operation — not independent reads and writes exposing the token bucket's internals across a network boundary.
