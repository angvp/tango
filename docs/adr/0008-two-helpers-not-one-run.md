# Two small helpers (`DispatchFlags` + `Serve`) instead of one `tango.Run`

Scaffolded projects needed to cut the ~120 lines of repeated boilerplate in every scaffolded `main.go` (CLI flag parsing for `-check`/`-tango-dump-models`/`-tango-status`/`-migrate`, plus registry/store/serve wiring). We considered a single do-everything `tango.Run(config, sqlDB, dialect, migrations) error` that would handle flag dispatch and serving internally, but rejected it: it would make `main()` no longer visibly show whether a given run checks flags, dumps models, or serves HTTP — exactly the "hidden dispatch layer" ADR 0001's plain-Go principle already rules out. Instead, `main()` calls two smaller helpers explicitly and in the order that matters: `tango.DispatchFlags(...)` (handles the CLI flags and reports whether it did) followed, only if unhandled, by `tango.Serve(config, sqlDB, dialect) error` (registry build, store wiring, `ListenAndServe`). `tango.ServeContext` later added the same shape with a `context.Context` for graceful shutdown; see [ADR 0031](0031-shutdown-uses-two-independent-phase-timeouts-and-a-decoupled-application-context.md). This cuts the real repetition without hiding the control flow a reader most needs to see.
