# Lifecycle components register explicitly through `Registry`, not an optional `App` interface

`Registry.RegisterLifecycle(Lifecycle)` registers a component with an optional `Start`/`Stop` pair, explicitly, inside `App.Register` — rather than reusing the `Checker` shape (an optional interface, type-asserted from each installed `App` in `Registry.Checks()`). The `Checker` pattern was the obvious first template to reach for: it is already exactly "an app optionally implements an interface, the registry finds it via a type assertion, in registration order." We rejected it for lifecycle specifically because `Checker` names passive metadata — an app either has advisory checks to report or it doesn't, and there is exactly one `Checks() []AppCheck` per app. Lifecycle components are not metadata: they own goroutines, ordering, rollback-on-failure, and independent shutdown behavior, and a single app frequently owns more than one of them (a chat app might own both a `realtime.Hub` and a background scheduler). Forcing "one implicit `Start`/`Stop` pair per `App`" would make that either impossible or push hosts toward one `App` per component purely to satisfy the interface shape — an artificial split with no other justification.

`Lifecycle{Name, Start, Stop}` registered via an explicit call sidesteps this: an app can register as many named components as it actually has, `Start`/`Stop` are each independently optional (a `Stop`-only `Lifecycle` is exactly what wrapping an already-constructed `realtime.Hub` needs — see `examples/realtime-chat`), and `RegisterLifecycle`'s own validation (non-empty `Name`, at least one non-nil callback, `ErrDuplicateLifecycle` on a repeated name) gives every component an identity useful in startup/rollback/shutdown error messages — something an anonymous `Checker`-style type assertion has no natural place to put. `App.Register` stays exactly as declarative as it is today: `RegisterLifecycle` records a component, it never starts one.
