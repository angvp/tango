# Permissions ship admin-only, as two boolean tiers, not a per-model matrix or an app-level primitive

Permissions were first framed broadly: "a tanGO app can require login or a named permission on a route," admin CRUD enforcement, and open questions about groups/roles and DB-vs-Go storage. Design review narrowed this to a much smaller, three-part scope decision, each part hard to reverse once ecosystem code depends on it, each a genuine trade-off with real alternatives on the table.

**Admin-only — no app-level permission primitive.** [ADR 0017](0017-app-auth-ships-primitives-not-a-model-or-interface.md) deliberately committed tanGO to owning no app User model or interface. A generic "require named permission" primitive for ordinary apps would need *something* to hang the check on — either a new required interface (`HasPermission(name string) bool`) or a fixed-field-name convention like the session-model precedent — either way, a second opinion about app User shape immediately after ADR 0017 avoided having a first one. `AdminUser`, by contrast, is framework-owned, so admin-side permissions cost nothing extra in scope. An app wanting role/permission checks writes its own [View wrapper](../reference.md) against its own User struct's own fields — already fully possible today, and exactly the kind of business logic tanGO's existing non-goals ("no automatic permission inference for arbitrary business logic") already say isn't tanGO's to own.

**Two boolean tiers (`IsStaff`, `IsSuperuser`) on `AdminUser`, not a per-model CRUD matrix.** A full Django-style `Permission`/`Group` matrix (view/add/change/delete per admin-registered model) is a real, ongoing schema commitment — new models, a UI to assign them, and migration churn every time a project registers a new admin model. `IsStaff` (can access the admin panel at all) and `IsSuperuser` (reserved for future finer-grained bypass) is the smallest change that makes "admin CRUD respects permissions consistently" true and demoable today, matching the stated non-goals ("no groups/roles UI unless design review proves it's required," "no object-level permissions unless a concrete admin case forces it"). Neither goal was proven, so neither shipped.

**`IsSuperuser` ships now, ignored.** `requireSession` checks only `IsStaff`; `IsSuperuser` has no distinct observable behavior and does not bypass `IsStaff` — a non-staff account with `IsSuperuser=true` still gets `403 Forbidden`, exactly like any other non-staff account. It ships anyway, documented plainly as a forward-compatible placeholder, because adding a boolean column later (once a future feature gives it something to bypass) would otherwise force every existing tanGO project through a second schema migration for one field. The alternative — shipping `IsStaff` only, deferring `IsSuperuser` until it means something — was rejected as needless churn for a cost (one inert column, clearly documented) that's already close to zero.

**Backward compatibility over secure-by-default.** The migration adding these columns backfills every existing `AdminUser` row to `IsStaff=true, IsSuperuser=true`, and `tango admin create <username>` defaults to the same, with `-tango-admin-no-staff`/`-tango-admin-no-superuser` as the explicit opt-out. The alternative (default `false`, requiring an explicit grant) was rejected because `tango admin create` has always meant "create someone who can administer the site" — a migration that silently locks out every account that worked yesterday, or a `create` that produces a login that can't actually do anything, are both hostile surprises with no real safety benefit here (there's no separate step where "create an account" and "grant it access" are meaningfully different operations yet, since there's nothing finer-grained to withhold).

Considered and rejected, together: an app-level `HasPermission` interface or fixed-field-name convention; a full per-model `Permission`/`Group` matrix; deferring `IsSuperuser` until it has real behavior; secure-by-default (`false`) for new accounts and existing-row backfill. All four would have made permissions a bigger, more speculative commitment than "give admin the two flags it can act on today."

**Extended by [ADR 0020](0020-accounts-is-a-conventional-identity-app-not-an-app-permissions-framework.md):** the optional `accounts` app keeps the same rule. Its `Account` model carries no permission fields either.
