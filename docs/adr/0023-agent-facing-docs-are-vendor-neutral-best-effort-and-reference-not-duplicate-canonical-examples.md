# Agent-facing docs are vendor-neutral, best-effort, and reference canonical examples rather than duplicating code or building sync tooling

`AGENTS.md` and `docs/agents/` are compact, task-oriented documentation for coding agents, distinct from tanGO's existing human-oriented `docs/guides/`/`docs/tutorial/`. Three shapes for this were genuinely open, and each has an obvious-looking alternative a future maintainer might reach for without the context below.

**Decision 1: one vendor-neutral `AGENTS.md`, never tool-specific files or sections.** No `CLAUDE.md`, no Codex-specific doc, no per-tool branching inside the file. This is a deliberate stance that tanGO should have one source of agent guidance, not one per agent brand — not a bet on which tools currently happen to auto-discover a given filename. Framing it as "because tool X reads this filename today" would be the wrong justification: tool support for any given filename convention can change, and a framework whose own stated philosophy is "no hidden configuration" (`README.md`) shouldn't fork guidance by which agent is reading it regardless. If a genuine tool-specific quirk ever matters, it gets one labeled paragraph inside the single file, not a parallel doc tree.

**Decision 2: recipes reference real, canonical, tested files under `examples/*` plus a tiny inline skeleton, never a full duplicated code block — and this is a maintenance obligation, not a one-time trick.** The temptation is to treat "point at a real file" as self-certifying: the path exists, so the doc must be accurate. It isn't. A referenced example can be renamed, restructured, or evolve in ways that leave the recipe's surrounding prose describing a shape the example no longer has, while the path itself still resolves. The decision here is specifically that canonical examples reduce (they eliminate the "duplicated code block quietly drifts from the real API," a certainty given tanGO's own "early, API still settling" status) but do not eliminate the staleness risk — the risk moves from the code block to the prose around the reference, and that residual risk is accepted deliberately, not overlooked.

**Decision 3: no automated doc-path or staleness validation — synchronization is a documented contributor review rule instead.** A test that parses `docs/agents/*.md` and confirms referenced paths still exist was considered and explicitly rejected: it would add a Markdown-parsing convention and a new category of test to maintain, and it only catches dead paths — not the more important failure mode from Decision 2, where a path still resolves but no longer demonstrates what the recipe claims. Since the cheap mechanical check doesn't address the failure mode that actually matters, and the failure mode that does matter isn't mechanically checkable without real content-diffing (out of scope here), the project accepts plain review discipline instead: changing a canonical example or a relevant public API obligates reviewing affected `docs/agents/` recipes, stated explicitly as a contributor rule. This can be revisited if repeated drift in practice demonstrates the tooling would actually pay for itself — but that's a future decision made on evidence, not a speculative build now.

**The common thread, and the trade-off accepted across all three:** agent docs stay a lightweight, best-effort layer — one file, real references, human review — rather than a small framework of their own (multi-tool variants, a machine-readable contract, a doc-linting pipeline). Less agent-doc-infrastructure now is worth more than building mechanisms for a drift problem that hasn't yet been observed to recur.

**Amendment (Decision 3):** two mechanical checks now exist, because the evidence the decision asked for arrived. A broken link shipped in the docs for weeks without review catching it, and the tutorial is now backed by a real app, `examples/board`, that its code can be compared against. First, CI runs `lychee --offline --include-fragments` over all of the repo's Markdown, so a relative link to a missing file or a missing `#anchor` fails the build; external URLs are not checked. Second, a Go test compares tutorial code blocks with `examples/board`: a block whose first line names a file (`// apps/posts/app.go`) must appear in that file verbatim, ignoring whitespace differences, and a block that shows an earlier state is exempt only if its label says `(as of part N)`. Neither check covers what Decision 2 is about: a reference that still resolves while the prose around it describes a shape the example no longer has. Keeping `docs/agents/` prose in step with the examples and public API is still the contributor's job at review time.
