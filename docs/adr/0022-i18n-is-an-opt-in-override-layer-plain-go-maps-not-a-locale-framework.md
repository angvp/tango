# `i18n` is an opt-in text-override layer built on plain Go maps, not a locale framework

`i18n` gives tanGO's framework/admin UI text — and any host or reusable app's own text — a translation path. The obvious reference points are Django's `gettext`-based i18n (a full extraction/`.po`/`.mo` pipeline with pluralization and locale-aware formatting) and Go's own `golang.org/x/text` (a comprehensive, `language.Tag`-driven catalog and formatting library already present as an indirect transitive dependency via tanGO's TUI stack, though unused directly anywhere in the framework). Either would be the "batteries-included" choice a framework author reaching for i18n typically makes.

**The decision: `i18n.T(ctx, key, fallback, args...)` resolves a key against plain `map[string]string` Go-source catalogs, falls back to the caller's inline English string when no locale, catalog, or key is found, and does nothing else.** No `x/text`, no gettext/`.po`/`.mo`, no file loading or parsing, no pluralization, no locale-aware date/time/number/currency formatting, no compile-time key generation. Catalogs are registered explicitly via `i18n.RegisterCatalog(locale, catalog)`, independent of the `tango.App` interface and `InstalledApps`, and merged per-key across repeated calls so registration order never matters. Locale resolution is a pluggable `func(*http.Request) string`, threaded through the request via a `tango.Middleware` and stdlib `context.Context` — never a new field on `tango.Context`, never coupled to `accounts`, sessions, or cookies. Admin's own templates call `i18n.T` unconditionally but never wire the middleware themselves: with nothing configured, every call resolves to its English fallback, so an admin installed today with zero i18n awareness behaves exactly as it would without `i18n`.

**English is never itself a catalog.** The fallback argument to every `T` call — the literal string already in the Go source — is the permanent last-resort default. Catalogs exist only to override it for a resolved locale; there is no separate "default locale catalog" that could drift out of sync with the code, and a catalog covering only a handful of keys is safe by construction rather than needing to be complete.

**Why not `x/text` or gettext now:** tanGO's entire current translatable surface is admin's own UI text — on the order of a couple dozen short strings, all Go template literals, no `.html` files. That scale doesn't justify a catalog-generation toolchain, a new build step, or a message-compiler dependency; it justifies the smallest thing that actually works. `x/text` and gettext both bring real machinery (locale negotiation, plural rule tables, message compilation) nothing in tanGO has a consumer for yet. Adopting either now would mean guessing at the shape of formatting and pluralization support before a real requirement forces the shape, which is the same mistake ADR 0019 and ADR 0020 already declined to make for permissions.

**The trade-off is intentional and accepted:** catalogs being Go source means a non-Go-literate translator cannot edit them directly, and the lack of pluralization or locale-aware formatting means this is a text-substitution layer, not a translation-management system. Both are addressable later — file-based catalog loading can sit on top of the same `RegisterCatalog` API without changing `T`'s signature, and formatting can be added once a real display-formatting surface exists to convert — without reworking anything this ADR commits to. Less i18n-framework complexity now is worth more than pre-building machinery for requirements no project has yet.
