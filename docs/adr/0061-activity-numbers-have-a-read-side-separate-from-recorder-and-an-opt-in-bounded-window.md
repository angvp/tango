# Activity numbers have a read side separate from Recorder, and an opt-in bounded in-memory Window

`observability.Recorder` is write-only by design. It receives bounded, redacted events and promises nothing about storage, aggregation, retention or querying, so an application can send its events to any exporter without that exporter holding state. An admin dashboard that shows recent request volume, error classes, latency and job outcomes needs to read those numbers back. If the dashboard read them from the Recorder, every Recorder would become a store: `NopRecorder` and every custom exporter would have to allocate, retain and sometimes run goroutines for a page most applications never open. The read side is therefore a separate interface, and the framework ships one bounded collector that implements both sides, with the dashboard opt-in.

`observability.Snapshotter` is the read side. Its `Snapshot() (Snapshot, error)` returns a bounded view of recent activity. The error is part of the contract, because a source backed by a shared store can fail, and the dashboard has to be able to show that failure instead of guessing. A `Snapshot` says what it covers: a `Scope` label supplied by the source, the `Since` time at which the activity window began, the `Window` length, request counts by status class with latency p50, p95 and p99 in seconds and the sample `Total` behind them, and job counts by outcome (success, error, panic, canceled). `Since` is the start of the activity window. It is not the start of the process, which the host's status provider reports separately.

`observability.Window` is the opt-in, in-process collector. It implements `Recorder` and `Snapshotter`, keeps 60 one-minute buckets, and uses fixed histogram buckets for percentiles. It keeps global aggregates only. It retains no route pattern, method, raw status code, user identifier, room identifier or job name, so no part of the framework's stored state can carry a value the bounded-label rule forbids. It resets when the process restarts, and its scope label reads "this instance only, since <start>". The Window is the only source the framework provides, and an application may supply a different one.

`observability.Multi(recorders ...Recorder)` fans one event out to several recorders in call order and ignores nil ones. It does not recover panics. A broken exporter stays visible to the caller, as it was before the fan-out existed.

The admin dashboard is enabled by the host. `admin.WithDashboard(admin.DashboardConfig{Status, Activity})` takes two optional sources, and either may be nil. `Status` is a host-supplied function that returns `admin.DashboardStatus`, a plain value with the database reachability, the dialect, applied and pending migrations, the tracking-table kind, the release and the process start time. It carries no error strings, DSNs, credentials or host metadata. The framework draws no status card on its own. Without a status provider, the status cards are absent or say "not configured", and they never claim health. `/admin/` renders the dashboard only when the host passes a configuration with at least one source. Otherwise it keeps its existing redirect to the first model. The dashboard sits behind the existing staff protection and adds no permission model.

A failing source does not fail the page. A callback that returns an error or panics is recovered at the dashboard boundary, logged on the server with its detail, and rendered as that card's generic "unavailable" state. Raw error text never reaches the page. Every activity number carries the source's own scope label, and the dashboard adds no claim of its own. Sample counts appear beside each percentile, and zero is shown as "no requests yet". Realtime room events are not shown; they remain available to external recorders only.

Rejected:

- **A stateful Recorder.** Making `Recorder` store and aggregate would give every implementation storage, retention and allocation costs, including applications that never open the dashboard, and would blur a write contract that existing recorders already implement.
- **Host-supplied sources only, with no shipped collector.** Each application would have to build its own bounded aggregation before the dashboard showed anything, and the privacy properties of the activity view would depend on each application's code rather than on the framework.
- **Cards the framework always draws.** A card for database reachability or migrations would claim health that the framework cannot check without a host-supplied source. A card with no data would look like a healthy one.
- **Labelled dimensions with an overflow bucket.** Per-route or per-job counters would need a label set that is either unbounded, which the privacy rule rules out, or capped, which keeps the names of the routes and jobs that filled the cap. The Window has no unbounded dimension, so it has no overflow bucket. A later decision that adds a bounded label can add one.

Consequences: the numbers describe one process since its last start. A deployment with several instances shows one scope per instance, the dashboard says so, and there is no fleet-wide view. The Window holds at most 60 minutes and nothing survives a restart, so there is no history, and it cannot say which route is slow, only how requests are distributed by status class and latency. A shared `Snapshotter` may fail, and the dashboard shows that card as unavailable. Existing recorders keep working unchanged, and an application that does not opt in gets the same `/admin/` redirect as before. Applications that need history, alerts or fleet-wide views should use an external monitoring system.
