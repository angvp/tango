# Admin extensibility ships best-effort, not as a stable contract

Admin extensibility adds a real public surface — the `Widget` interface, four new `admin.Options` fields (`Labels`/`HelpText`/`ReadOnly`/`FieldOrder`, alongside `Widgets`), the built-in widgets, and `admin.WithBranding` — but it is declared **best effort**, not folded into the same stable-contract commitment `docs/limitations.md` already makes for the CLI app-side flags (`-check`, `-migrate`, etc.), where breaking changes must be called out ahead of time.

This is deliberate, not an oversight: admin's internals (its template rendering, its default field behaviors, its theme) are still expected to evolve as real usage surfaces gaps, and locking this specific surface to the advance-notice process now would either freeze admin's evolution prematurely or force a confusing "stable API, unstable implementation" story. Best-effort is also distinct from `docs/limitations.md`'s existing "APIs still expected to change before a stable release" section — that section names things expected to *settle* before a stable release. Admin extensibility is expected to keep evolving even after a stable release ships, because admin itself is the part of tanGO most likely to keep growing.

Considered and rejected: treating the `Widget` interface as stable while leaving only the built-in widgets' markup/branding as best-effort (a split that was considered) — rejected in favor of one simple rule covering the whole surface, since a caller who can't tell which half of "admin extensibility" is which gets no real benefit from a partial commitment.
