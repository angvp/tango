# Job failure reporting suppresses only errors matching the Application context's own cancellation

A `Job.Run` that returns an error gets logged via `reportJobFailure` — except when that error actually represents the Application context being canceled out from under it: `appErr := appCtx.Err(); appErr != nil && errors.Is(runErr, appErr)`. This mirrors `ServeContext` already treating `http.ErrServerClosed` as expected termination rather than a real failure: a cooperative `Run` that stopped *because the app is shutting down* isn't a failure a host can act on, and logging one "job failed" line per in-flight job on every graceful shutdown would be pure noise.

The check is deliberately narrower than "suppress every `context.Canceled`." A `Job` is free to make its own independent calls with their own, separately-canceled contexts while the Application context is still fully live — a `Run` that returns `context.Canceled` in that situation is a real failure (a bug, a timeout the host configured itself, anything) and must still be reported. Suppressing on the error *type* alone would hide those. Checking `errors.Is(runErr, appCtx.Err())` specifically ties suppression to *this* cancellation, not cancellation in general — and since the Application context is `context.WithoutCancel` plus a plain `context.WithCancel` (never a `WithDeadline`/`WithTimeout`), its own `Err()` is always exactly `context.Canceled`, never `context.DeadlineExceeded`, so a host-created per-run timeout stays reportable by construction, not by a special case. A recovered panic is never suppressed by this rule, regardless of Application-context state — shutdown must never hide a real panic.
